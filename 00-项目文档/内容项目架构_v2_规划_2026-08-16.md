## 2. 控制流：MANIFEST.yaml 作为公共契约

### 2.1 为什么要 MANIFEST？

4 个核心需求：
1. **避免重复生产** — autoclaw 知道哪些概念已做
2. **质量可监控** — pass_rate 持续跟踪
3. **进度可视化** — done / in_progress / pending
4. **故障定位快** — autoclaw 死在哪一步能查

### 2.2 MANIFEST 结构

详见 [MANIFEST.yaml](./MANIFEST.yaml)，关键字段：
- `version` / `schema_version` / `last_sync`
- `subjects`（学科总览 + 质量数据）
- `consumption_profiles`（应用场景：app_training / writing_material / feynman）
- `roles`（3 个角色的权责边界）
- `workflow`（11 步流程）
- `snapshot`（当前已上架的卡）

### 2.3 协商流程

```
[autoclaw]                          [本机 Mavis]                  [GitHub]
   1. git pull 读 MANIFEST
   2. 选 done=false 的概念
   3. 改 MANIFEST in_progress=true
   4. 产 1 套 JSON
   5. 跑 _validate_cards.py
   6. 改 MANIFEST done=true + 时间戳
   7. git commit + push  ─────────────────────────────────→  [main 推进]
                                                                       │
                                                            8. git pull  ←┘
                                                            9. 跑校验
                                                           10. 更新 last_sync
                                                           11. 推 rujing
```

**关键规则**：
- autoclaw 改 MANIFEST 的 `in_progress` / `done` / `quality.last_validate`
- Mavis 改 MANIFEST 的 `last_sync` / `pass_rate` / `shipped_to_rujing`
- willi 看 MANIFEST 决定 status 升级（draft → trial → certified）

## 3. 多学科/多项目：单仓库多学科

### 3.1 为什么是单仓库？

| 方案 | 优点 | 缺点 | 推荐度 |
|:---|:---|:---|:--:|
| **A. 单仓库多学科** | 统一规范、共享工具、跨学科复用、MANIFEST 全局视角 | 仓库变大、PR 冲突 | ⭐⭐⭐ |
| **B. 多仓库** | 完全解耦、独立演进 | 规范更新要 N 次同步、工具重复 | ⭐ |

**选 A 的 4 个理由**：
1. **共享工具**：`_tools/_validate_cards.py` 一次写好、所有学科用
2. **跨学科复用**：同主题/同朝代跨学科 K 卡片可以互相引用
3. **统一 MANIFEST**：一眼看所有学科进度
4. **规范同步**：v1.0 升级时只改一个文件

### 3.2 仓库目录结构

```

│   ├── 知识卡片架构_v2_规划.md   ← 本文件
```

## 4. 多场景：1 套规范 + N 个 Profile

### 4.1 三种消费场景

| Profile | 用途 | 消费端 | 与本征层关系 |
|:---|:---|:---|:---|
| **`app_training`** | 推 rujing APP（高考应试 / 学科速查） | rujing APP | 从本征层派生：拆 back_detail 短问短答、生成 Q&A 原子 |
| **`writing_material`** | 写作素材库（编剧 / 创作 / 跨学科缝合） | 写作工具 | 在本征层加：materials.data / 跨书引用 / audience 标签 |
| **`feynman`** | 费曼讲解（教学复盘 / 检验真懂） | 教学平台 | 在本征层加：teaching_hooks / 听众画像 / 简化版 |

### 4.2 双层架构（本征层 + 应用层）

```
本征层（autoclaw 产）
  ↓ 知识原子（不变）
  ↓ - card_id / 核心事实 / sources / concepts
  ↓ - front 短问 + back_core 短答
  ↓
应用层（Mavis 派生）
  ↓ - app_training：拆 back_detail → Q&A 原子
  ↓ - writing_material：加 materials.data + 跨链
  ↓ - feynman：加 teaching_hooks + 听众画像
  ↓
消费端
  ↓ - rujing APP（高考应试）
  ↓ - 写作工具（编剧/创作）
  ↓ - 教学平台（费曼讲解）
```

**这与 2026-08-07 你确立的"双层架构"完全一致**：
> 本征层（知识原子，不可变）：card_id / 核心事实 / sources[] / concepts[]
> 应用卡（根据方向生成不同内容）：
> - 考试卡：Q&A原子化，back≤200字
> - 素材卡：叙事完整，back可长，materials层，多链归属
> - 费曼卡：听众画像+teaching_hooks
